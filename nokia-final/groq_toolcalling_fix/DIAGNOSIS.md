# Groq Tool-Calling Diagnosis

## Scope and protection

This is a read-only diagnosis. No existing project source, configuration,
environment file, test, or database record was modified. This directory was
available and was created only for this proposal, its local test contract, and
mocked tests.

## Actual application path

The browser route is the Groq add-on path:

```text
secure-access-ai/src/pages/AIAssistantPage.jsx
  -> secure-access-ai/src/api/aiAssistant.js: askGroqAssistant
  -> POST /groq-ai-api/api/chat
  -> secure-access-ai/vite.config.js proxy
  -> Groq add-on POST /api/chat (groq_ai_addon/backend/app.py)
  -> ChatbotService.answer
  -> GroqProvider.complete
  -> Groq Python SDK chat.completions.create
  -> Groq Chat Completions API (SDK default base URL)
```

The separate `POST /ai-api/chat/query` route is the standard Secure Access API
chatbot and is not the route used when the UI's Groq mode is selected.

The active add-on is configured from its `--env-file` at
`groq_ai_addon/.env`; the effective `GROQ_MODEL` value is
`openai/gpt-oss-120b`. This was read without printing or sharing the API key.
The provider does not request streaming (`stream` is omitted, so the API
default is false), and does not set a JSON response format.

## Error evidence and root cause

The displayed text is generated by `GroqProvider.complete` for every HTTP 400.
That handler logs only exception class and status, then replaces the provider's
specific error body with:

> Groq rejected the request format. Check model tool-calling support and the
> configured tool schema.

Consequently, the screenshot alone does **not** establish the current
provider-side cause. The exact failed request, HTTP response body, provider
error code, and tool-call round are not retained in the UI error. The running
process's past failing request could not be recovered from its logs.

One earlier error was independently reproduced with a synthetic request:
`tool_choice="required"` can return HTTP 400 when GPT-OSS does not emit a call
(`Tool choice is required, but model did not call a tool`). The current source
uses `tool_choice="auto"` for tool-bearing requests, so that earlier condition
does not explain this screenshot unless a stale process/request used the old
code.

After local schema validation, a current, evidence-free Groq request using the
actual model, the risk-question tool subset, `tool_choice="auto"`, and
`parallel_tool_calls=False` was accepted and returned a call to
`analyze_ssh_command_archive`. A second synthetic end-to-end chatbot probe
completed its tool round-trip. These results show that this current model and
basic tool-request shape work; they do not identify the contents of the
unavailable failing request or prove every tool/message history valid.

For “explain recent high risk sessions”, current source performs a deterministic
archive query and returns its formatted result without calling Groq. If the
displayed HTTP 400 followed that exact question, it is consistent with an
older running add-on, another endpoint/provider mode, or a different request;
request-time diagnostics are needed to distinguish these.

## Schema audit

Local validation of all 12 `TOOL_DEFINITIONS` passed:

- Envelope is `{"type":"function","function":{...}}`.
- Function names are unique and valid; every function has a nonempty
  description and object-valued `parameters`.
- Parameter schemas use JSON Schema types, including valid nullable
  unions such as `["string","null"]`.
- Every `required` field is declared in `properties`.
- Current schema keywords are standard annotations/constraints or object
  controls: `description`, `default`, `enum`, `type`, `properties`,
  `required`, `additionalProperties`, numeric bounds, and string-length bounds.
- No `$ref`, accidental JSON-string/double encoding, or unknown keyword was
  found by the local supported-keyword audit.
- All tools serialize to 6,291 UTF-8 bytes. Groq's API reference documents a
  maximum of 128 function tools; the complete list has 12 and the chatbot
  selects a question-relevant subset.

This is a local structural audit against the JSON Schema subset in this
proposal. It is not proof that Groq accepts every model-produced payload or
argument.

## Tool history audit

The implementation converts each returned call into an assistant message with
the call ID, function name, and JSON argument string. It then appends one
`role="tool"` result per call with the corresponding `tool_call_id`, tool name,
and JSON-serialized sanitized result before the next completion. Tool arguments
are parsed and Pydantic-validated by `ToolRegistry`; evidence is sanitized,
bounded to 10,000 characters per result and 32,000 characters cumulatively.
The requested tool schemas are bounded to 12 maximum and generated from the
allowlist.

The loop does not independently validate response call IDs for uniqueness,
function-call structure, or argument JSON before writing the assistant tool
message. Tool-call outcomes that raise a registry/data-source error abort the
round and become an API error; no follow-up provider request is made with an
orphan result. With GPT-OSS, parallel calls are explicitly disabled, but the
implementation can serialize a response containing multiple calls by appending
one corresponding result for each before requesting the next model turn.
Regression tests below characterize these behaviors and identify validation
that should be added.

## Official compatibility evidence

Checked official Groq documentation on 2026-10-25:

- Tool-use overview says all Groq-hosted models support tool use.
- Its model matrix lists `openai/gpt-oss-120b` as supporting local/remote tool
  use and JSON mode, but not parallel tool use.
- The Chat Completions API reference lists `tool_choice` options including
  `auto`, `none`, and `required`; `auto` is the default when tools are present.
- The API reference describes `parallel_tool_calls` and a maximum of 128
  function tools.
- The current application uses Chat Completions, automatic tool selection,
  no JSON response format, no streaming, and explicitly disables parallel
  tool calls when tools are included.

Sources:

- [Groq tool-use overview](https://console.groq.com/docs/tool-use/overview)
- [Groq Chat Completions API reference](https://console.groq.com/docs/api-reference#chat-create)
- [Groq models](https://console.groq.com/docs/models)

## Conclusion

The configured model is supported for local tool calling, and all tool
definitions passed the local structural audit. A current, synthetic Groq tool
request was accepted. The exact cause of the screenshot's HTTP 400 remains
**unestablished** because the current application discards the provider error
body and no contemporaneous failed request is available. Do not claim the
current generic 400 is fixed or change model/schema based on this evidence
alone.
